## 症状
TTS 播放**短句**（< ~1.5s）一切正常，对话能正确进入下一轮；播放**长句**（≥ 3s 的 LLM 长回复）时，串口可观察到：
1. 服务端 `TTS_STOP` 事件已到达
2. 喇叭仍在继续放后半句
3. 紧接着出现 `检测到说话结束（VAD 静音 600ms），通知服务器`
4. 服务端把残音当成 ASR 输入，回了一段莫名其妙的"新回答"

## 根因（三层漏洞链）

### 漏洞 ① TTS_STOP ≠ 本地真正播完
[session.c:633-666](main/session/session.c#L633-L666) 中 `PROTOCOL_EVENT_TTS_END` 立即把 `s_state` 切回 `LISTENING`，但本地下游有三层缓冲：
- `dec_input`（NOSPLIT 16KB，未解码 OPUS，约 5s 容量）
- `dec_output`（BYTEBUF 40KB，已解码 PCM，约 1.28s）
- I2S DMA + 喇叭物理振膜

长句下游可能还堆着 2~3 秒数据没播完。

### 漏洞 ② 1500ms 兜底对长句失效
[session.c:368-406（旧版）](main/session/session.c#L368-L406) 排空判定：
```c
if (s_vad_silence_count > 8) { ... 排空完毕 ... }  // 需要连续 8 帧 VAD_SILENCE
if (wait_ms > 1500) { ... 强制开监听 ... }         // 兜底超时
```
长句残留持续大能量音频 → VAD 一直判 SPEECH → `s_vad_silence_count` 一直归零 → 1500ms 兜底触发时喇叭仍在响。

### 漏洞 ③ 仅靠 VAD 判排空，没读解码器水位
旧版完全没用 `vRingbufferGetInfo` 读 `dec_output` 字节数，明明能直接知道"还有多少 PCM 没播"。

## 修复

### 改动 1：audio_processor 暴露解码链路水位接口

[audio_processor.h:196-214](main/audio/audio_processor.h#L196-L214) 新增声明：
```c
size_t audio_processor_get_pending_bytes(audio_processor_t *audio_processor);
```

[audio_processor.c:493-516](main/audio/audio_processor.c#L493-L516) 实现：
```c
size_t audio_processor_get_pending_bytes(audio_processor_t *p) {
    if (p == NULL) return 0;
    size_t dec_in = 0, dec_out = 0;
    if (p->dec_input)  vRingbufferGetInfo(p->dec_input,  NULL, NULL, NULL, NULL, &dec_in);
    if (p->dec_output) vRingbufferGetInfo(p->dec_output, NULL, NULL, NULL, NULL, &dec_out);
    return dec_in + dec_out;
}
```

### 改动 2：session.c 排空"三重锁"

[session.c:368-417](main/session/session.c#L368-L417) 重写排空判定：
- **锁 1**：物理静音 ≥ 400ms（振膜余波兜底，保留）
- **锁 2**：`audio_processor_get_pending_bytes(s_processor) == 0`（**新增**）
- **锁 3**：连续 8 帧 VAD_SILENCE（保留）
- 三者**同时**成立才认定排空完毕
- 兜底超时 1500ms → **5000ms**（覆盖最长 TTS 句子的下游缓冲深度）

关键代码：
```c
size_t pending_bytes = audio_processor_get_pending_bytes(s_processor);
if (vad == VAD_SILENCE) {
    s_vad_silence_count++;
    if (s_vad_silence_count > 8 && pending_bytes == 0) {
        s_waiting_for_silence = false;
        ESP_LOGI(TAG, ">>> 扬声器排空完毕 (耗时 %d ms, pending=0)，开启监听 <<<", (int)wait_ms);
        s_vad_ready_tick = xTaskGetTickCount();
    }
}
...
if (wait_ms > 5000) { /* 强制开监听，并打印残余 pending 字节数便于调参 */ }
```

## 验证
- 编译通过（`idf.py build`，Echo.bin 0x290330，15% 余量）
- 待实测：长句对话场景是否消除"残音变下一轮提问"现象。

## 启示
- **服务端控制事件**（TTS_STOP）**永远不等于本地物理完成**。所有"播放结束"判定都必须叠加本地下游链路状态。
- **AEC 是补刀，不是主防御**。AEC 对高能量持续信号消除残量有限，主防御必须是"不让残音进入麦克风采集流"。
- 排空判定不要只信 VAD/物理静音单一指标，**多维 AND**（缓冲水位 + VAD + 时间）才稳。
