# BUG-015：GPIO14 FSPIWP 默认弱上拉引起 I2C NACK + 共 timer 舵机连锁失灵

## 现象
- 舵机引脚分配 GPIO 4/9/14（右臂+头+左臂），LEDC TIMER_0 共用
- 上电瞬间 I2C 设备（地址 0x30）报 NACK：
  ```
  E (15795) i2c.master: I2C transaction unexpected nack detected
  E (15795) I2C_If: Fail to read from dev 30
  ```
- 同时 GPIO 4 右臂舵机完全不动（连锁失灵）
- 实测：移除 GPIO 14 → 4/9 单独用一切正常；只要 14 加入就炸

## 根因
ESP32-S3 GPIO 14 官方手册功能字段：
```
GPIO14   I/O/T              ← 普通 GPIO，输入/输出/高阻
FSPIDQS  O/T                ← FSPI 数据选通（仅输出）
SUBSPIWP I1/O/T             ← Sub-SPI 写保护，I1=Default Input Level 1
FSPIWP   I1/O/T             ← FSPI 写保护，I1=Default Input Level 1
```

**关键字段 `I1`**：上电默认配置为「输入 + 弱上拉到 1」（约 45kΩ → 3.3V）。

**因果链**：
1. 上电瞬间 GPIO 14 被内部弱上拉拉到 3.3V
2. 舵机信号线持续高电平 → 舵机控制器识别为短脉冲 → 反复抖动
3. 舵机堵转电流可达 1A+ → 共用 3.3V 电源轨压降到 2.5V 以下
4. ES8311 / 触摸 IC 短暂掉电复位 → I2C 第一次握手不应答 → NACK
5. LEDC TIMER_0 在电源震荡时配置 GPIO 14 失败 → 共 timer 的 GPIO 4/9 也跟着挂

**为什么共 timer 一损俱损**：LEDC 同一 timer 的多通道初始化在 ESP-IDF 内部是原子事务，单通道失败会导致整个 timer 状态机异常。

## 修复方案（已实测有效，2026-05-14）

### 软件方案（已采用）
**前提**：PCB 已焊死，GPIO 14 无法换其他引脚。

**修复代码**：[main/application.c](main/application.c) `application_init()` 函数最开头，早于所有外设初始化：
```c
gpio_config_t io_conf_g14 = {
    .pin_bit_mask = (1ULL << GPIO_NUM_14),
    .mode         = GPIO_MODE_OUTPUT,
    .pull_up_en   = GPIO_PULLUP_DISABLE,    // 显式覆盖 FSPIWP 默认 I1=1
    .pull_down_en = GPIO_PULLDOWN_DISABLE,
    .intr_type    = GPIO_INTR_DISABLE,
};
ESP_ERROR_CHECK(gpio_config(&io_conf_g14));
gpio_set_level(GPIO_NUM_14, 0);
```

**为什么用 gpio_config 而非 3 行简写**（gpio_reset_pin + set_direction + set_level）：
- 显式禁用上下拉，不依赖 reset_pin 默认行为
- 显式禁用中断，避免 SUBSPIWP 残留中断
- 原子配置，无中间窗口
- ESP_ERROR_CHECK 静默错误暴露
- ESP-IDF 官方推荐标准写法

**安全性**：后续 `bsp_board_servo_init` 启用 LEDC 时通过 GPIO Matrix 重新路由 PWM 信号到 GPIO 14，覆盖此处输出状态，无冲突。

### 硬件方案（推荐补充，未做）
GPIO 14 → GND 飞线一颗 10kΩ 下拉电阻。彻底消除上电 50ms 软件未运行窗口的抖动。

## 5 个隐患清单

### ⚠️ 隐患 1：上电最初 ~50ms 软件未运行，仍有硬件抖动
- ROM bootloader → 二级 bootloader → app_main 入口约 50~200ms
- 这段时间 GPIO 14 仍被弱上拉到 3.3V，舵机仍会抖 1~2 次
- 长期反复可能加速齿轮磨损
- 彻底解决：硬件加 10kΩ 下拉电阻

### ⚠️ 隐患 2：启动顺序绝不能乱
- gpio_config 必须早于 `bsp_flash_init` / `audio_init` / `bsp_lcd_init`
- 未来重构 application_init 把它挪后 → NACK 立即复现
- 防御：[application.c](main/application.c) 已加防御注释；[bsp_config.h:166](main/bsp/bsp_config.h#L166) 引脚定义已标注

### ⚠️ 隐患 3：GPIO 14 与 FSPI/SubSPI 隐形复用风险
- 当前 LCD `quadwp_io_num = -1`（[bsp_lcd.c:51](main/bsp/bsp_lcd.c#L51)），未占用 GPIO 14
- 未来 LCD 升级 QSPI 模式或外部 Flash 改 Quad I/O → GPIO 14 被自动征用 → 与舵机 PWM 撞车
- 防御：引脚分配评审时必查 FSPI 配置

### ⚠️ 隐患 4：深睡眠唤醒可能复现
- 软件复位/异常复位走完整 app_main 流程 → OK
- Deep sleep 唤醒可能保留 RTC GPIO 状态，需专门验证
- 当前项目未用 deep sleep，风险等级低

### ⚠️ 隐患 5：掉电瞬间舵机抖动
- LEDC 停止后 GPIO 14 回到默认弱上拉 → 关机抖一下
- 多数场景可忽略；如需"优雅关机"，shutdown 钩子里再次 set_level(0)

## 拆 timer 方案（已否决，备查）

最初讨论过把 GPIO 14 拆到 LEDC_TIMER_1 隔离故障，**但探索 iot_servo 组件发现**：
- `managed_components/espressif__servo/iot_servo.c:25` 用 `static servo_config_t g_cfg[LEDC_SPEED_MODE_MAX]` 全局存储
- 同一 speed_mode 下只能存一套配置，第二次 `iot_servo_init` 会覆盖第一次
- `iot_servo_write_angle / read_angle` 都依赖该全局状态

可行替代：左臂绕过 iot_servo 直接用 `ledc_timer_config + ledc_channel_config + ledc_set_duty`，但要改 `bsp_servo_move_smooth` 分流逻辑，复杂度高。

**实测改动 1 已解决问题，此方案不必要**。保留备查。
