# BUG-011 音频任务 SPIRAM 栈泄漏

| 字段 | 值 |
|---|---|
| 编号 | BUG-011 |
| 状态 | 已修复 |

---

## 症状
多次发起 → 结束会话后，PRINT_MEM_INFO 打印的 SPIRAM free 单调下降，重启才恢复。
单次量级：encoder 32KB + decoder 32KB = **每次会话 64KB SPIRAM 泄漏**。

## 根因
`xTaskCreatePinnedToCoreWithCaps` 调用时 `pxCreatedTask` 参数传 `NULL`：
- decoder：[audio_decoder.c:308-315 旧](main/audio/audio_decoder.c)
- encoder：[audio_encoder.c:288-295 旧](main/audio/audio_encoder.c)

stop() 函数只是 `vTaskDelay(200ms)` 就返回，**不检查任务是否真的执行到了 vTaskDelete(NULL)**。
若任务此刻卡在 `xRingbufferReceive` 长超时 / 编码耗时未及时检测 `is_running=false`，stop() 已经返回 → 上层调 `audio_decoder_destroy()` free 实例 → 任务还活着但其参数指针已悬空 → 行为未定义；
更要命的是下次 `start()` 又分配新的 32KB SPIRAM 栈，旧栈永远不会被回收（任务确实 vTaskDelete 自己时栈才会归 IDLE 释放，但任务可能根本没退出，或者退出了 IDLE 没机会运行）。

## 修复
为两个任务都加 `volatile TaskHandle_t task_handle` 字段：
- decoder：[audio_decoder.c:51](main/audio/audio_decoder.c#L51)
- encoder：[audio_encoder.c:33](main/audio/audio_encoder.c#L33)

创建时保存句柄：
- decoder：[audio_decoder.c:316](main/audio/audio_decoder.c#L316)
- encoder：[audio_encoder.c:296](main/audio/audio_encoder.c#L296)

任务退出前主动清空句柄（在 `free` 之后、`vTaskDelete(NULL)` 之前）：
- decoder：[audio_decoder.c:204](main/audio/audio_decoder.c#L204)
- encoder：[audio_encoder.c:175](main/audio/audio_encoder.c#L175)

stop() 改为轮询 + 超时强杀：
- decoder：[audio_decoder.c:343-352](main/audio/audio_decoder.c#L343-L352)（10×20ms = 200ms 上限）
- encoder：[audio_encoder.c:320-330](main/audio/audio_encoder.c#L320-L330)（20×20ms = 400ms 上限）

```c
for (int i = 0; i < N && task_handle != NULL; i++)
    vTaskDelay(pdMS_TO_TICKS(20));
if (task_handle != NULL) {
    ESP_LOGW(TAG, "任务超时未退出，强制终止以释放 SPIRAM 栈");
    vTaskDelete(task_handle);
    task_handle = NULL;
}
```

附带：[audio_processor.c:271](main/audio/audio_processor.c#L271) destroy 后追加 `vTaskDelay(100ms)`，给 CPU0 IDLE 任务清理已 vTaskDelete 任务栈的时间窗，避免内存快照时序偏差。

## 验证
连续触发 5 次以上"唤醒 → 会话 → 关闭"，SPIRAM free 应稳定回到同一水位（±少量 ringbuffer/cJSON 缓存波动），不再单调下降。
若日志中出现 `WARN: ...超时未退出，强制终止以释放 SPIRAM 栈`，说明触发了兜底路径，应顺藤排查任务为何没在循环超时窗口内退出（可能 ringbuffer 消费方卡住或 codec 卡住）。

## 启示
- 凡是 `MALLOC_CAP_SPIRAM` 创建的任务栈，stop() 必须**确认任务真的 vTaskDelete 完毕**才能算停。普通 INTERNAL 栈也一样，只是 SPIRAM 量级 32KB 起，泄漏后果更严重。
- `xTaskCreatePinnedToCoreWithCaps` 与 `xTaskCreate` 不同，回收逻辑只跟着任务自己的 `vTaskDelete(NULL)` 走，外部很难做兜底，所以**保留句柄 + 强杀**是必备退路。
