# BUG-037 跳一跳「落空时像踩到透明台子平移一下」

## 一、现象

跳一跳蓄力不足/过头 → 没落到台子上 → **下坠过程中肉眼可见小人先横向平移一小段再往下掉**，观感像"跳到了一块透明台子上滑了一下"。非崩溃、非逻辑错误，纯视觉连续性问题。

## 二、根因（一句话）

`main/games/game_jump.c` 落空判定分支里 **`g.fall_vy = 0;`**，把飞行最后一帧本来已有的 ~14px/帧竖直下落速度清零，而水平速度 `fall_vx` 仍是 9px/帧 → 头 2~3 帧几乎纯横移。

## 三、量化推导（为什么恰好"贴着台面高度"）

1. 判定只在 `t=1` 做（`game_jump.c:1187-1191` 最后一步强制对齐终点），而终点 y 就是 `plats[1].world_cy`＝**目标台顶面高度** → 小人脚底精确停在台面高度。
2. 飞行阶段屏幕下落速度 = 每帧世界 y 位移 + 弧高降幅；末帧弧高从 `4*apex*(n-1)/n²` 掉到 0。
   代入 `apex = dist × JUMP_APEX_RATIO(40%)`、`n = dist / JUMP_FLY_STEP_PX(9)`：
   **该值与蓄力距离无关，恒约 12~14 px/帧**（dist=55→12.2，dist=150→14.1，dist=200→13.9）。
3. 旧代码进入 PH_FALL 后：

   | 帧 | 竖直 | 水平 |
   |---|---|---|
   | 飞行末帧 | ↓14 | →9 |
   | FALL 1 | ↓3 | →9 |
   | FALL 2 | ↓6 | →9 |
   | FALL 3 | ↓9 | →9 |

   竖直 14→3 骤降 ≈ 100ms（@30fps `JUMP_ENGINE_MS 33`）近似水平滑行，正好停在台面高度 → "透明台子"。

## 四、修复（已改·已编译·✅2026-07-31烧录实测通过）

| 文件:行 | 改动 |
|---|---|
| `main/games/jump_sprites.h:154-160` | 新增 `#define JUMP_FALL_GRAVITY 3`（原来重力 3 硬编码在两处），注释写清"初速不用它起跳" |
| `main/games/game_jump.c:1291-1310` 落空分支 | `fall_vy = 0` → `fall_vy = fly_total_y/n + 4*fly_apex*(n-1)/(n*n)`，并 clamp ≥ `JUMP_FALL_GRAVITY` |
| 同上 | `fall_h` 原用 `t256` 计算（**t256 恒为 256 ⇒ 结果永远 0，死代码**，注释声称的"残余弧高平滑接力"从未生效）→ 直接置 0 并注明 |
| `game_jump.c:1400-1418` PH_FALL | 两处硬编码 `3` 改 `JUMP_FALL_GRAVITY`；给 `fall_h>0` 死分支加"当前唯一入口恒为0，仅作防御"说明 |
| `game_jump.c:1301` 日志 | `h=%d` → `vy0=%d(接力飞行末帧速度)`，便于串口直接看接力值是否 ~12~14 |

编译：`idf.py build` 通过，`Echo.bin` 0x37d1b0（app 分区剩 0% 是既有问题，与本次无关）。

## 五、实测验证（2026-07-31 烧录·✅通过）

肉眼确认：落空下坠已是连续弧线，"贴台面横移一下"消失。串口证据：

```
I (63171) JUMP: 判定 actual_wx=271 next[162,214] overshoot=57 foot_half=8
I (63171) JUMP: 落空 wx=271 vx=8 vy0=11(接力飞行末帧速度)
I (63531) JUMP: 结算: 得分=0 历史最高=0（1000 ms 后自动重开）
```

三点对账：

1. **确属完全落空路径**：`overshoot=57` ≫ `topple_limit`（=`foot_half 8 × JUMP_TOPPLE_RANGE_PCT 100%` = 8）⇒ 走 `else` 进 PH_FALL，排除 PH_TOPPLE 干扰（用户亦当面确认"不是踩到台缘那条路"）。
2. **接力确实生效**：`vy0=11`，既非旧代码的 `0`，也非 clamp 兜底的 `3`。
3. **11 略低于预估 12~14 属正常，非打折**：公式含 `fly_total_y / n` 项，本次是**向上方台子跳**（fly_total_y 为负）故拉低几 px；同理 `vx=8 < JUMP_FLY_STEP_PX 9`，因 9 是沿飞行方向的步长，分解到 x 轴必然小于 9。数字自洽。

⇒ **调参提示**：若日后想让坠落更急，调 `JUMP_FALL_GRAVITY`（3→4/5）；`vy0` 若某次打出 `0` 说明改动没进固件（烧错），打出 `3` 说明接力公式算崩了走了兜底。

## 六、教训

- **抛物线飞行切换到自由落体，必须接力"末帧速度"，不能从 0 重新起加速**——加速度连续不代表速度连续，肉眼对速度突变极其敏感（此处仅 3 帧就能被看出来）。
- 死代码会伪装成"已经处理过了"：`fall_h = apex*4*t256*(256-t256)/...` 在 `t256==256` 处恒为 0，注释写着"平滑接力"，实际一行没生效，**掩盖了真正缺的速度接力**。查视觉手感问题时要把公式代入端点值实算一遍。
- 与 [[bug-022]] 同属"跳一跳视觉与判定/物理不连续"家族：BUG-022 是**位置**两套坐标打架（视觉飞台心/判定另算），本条是**速度**在相位切换处断裂。
