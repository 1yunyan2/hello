# BUG-008：定时器回调直接调 session_close() 导致栈溢出

## 基本信息

| 项目 | 值 |
|------|-----|
| 发现日期 | 2026-04-14 |
| 修复日期 | 2026-04-14 |
| 提交 | `c2df9e1` |
| 严重程度 | **致命**（设备死机） |
| 关联文件 | `main/session/session.c` — `on_session_timeout()` |
| 状态 | **已修复并提交** |

## 现象

会话超时（30 秒无活动）后设备死机重启。

## 根因

`on_session_timeout()` 是 FreeRTOS 软件定时器回调，运行在 **Timer Service Task** 上下文中。该任务栈较小（通常 2~4KB）。

`session_close()` 内部会执行：
- audio_processor drain（等待音频播放完毕）
- WebSocket 断开
- 多个 FreeRTOS 同步原语操作

这些操作的调用栈深度远超定时器任务栈空间 → **栈溢出 → 硬件看门狗触发重启**。

## 修复方案

```c
// ❌ 修复前：定时器回调中直接调用
static void on_session_timeout(TimerHandle_t t) {
    session_close();  // 栈溢出！
}

// ✅ 修复后：仅投递事件，由独立任务处理
static void on_session_timeout(TimerHandle_t t) {
    if (s_session_evt_queue != NULL) {
        session_evt_t evt = SESSION_EVT_CLOSE;
        xQueueSend(s_session_evt_queue, &evt, 0);
    }
}
```

`session_event_task` 拥有足够栈空间（通常 8KB+），安全执行 `session_close()`。

## 经验教训

> **FreeRTOS 定时器回调 = 轻量操作专属**。绝不在定时器回调中调用可能阻塞或深栈的函数。正确做法：投递事件/信号量，由独立任务处理。

同一原则适用于：ISR、事件循环回调等受限上下文。
