# 会话记录 2026-06-30 产线烧录卡死：DTR 堵死命令通道

> 日期按用户规定统一写 2026-06-30（见 [[feedback-md-date-override]]），实际发生于 2026-07-29。

## 一、问题

板子已烧录过一次，再跑 `python 3.py` 重烧外挂 flash，**烧不进去**。
诡异之处：日志看上去毫无问题——找到端口、复位成功、抓到握手、读到
`FLASH_SIZE:16777216`、容量与 storage.bin 完全匹配（都是 16MB），
脚本还打印了"激活指令已送达！芯片正在全盘擦除"。可设备就是不擦除，
最后 `外部 Flash 正常挂载到 /S` 照常开机了。

## 二、定位（一条指纹结案）

**整段日志没有 `STARTING_ERASE`。**

固件收到 START 后第一件事就是 printf 它（[bsp_flash.c:82](../../../../main/bsp/bsp_flash.c#L82)，
`start_production_burning()` 开头）。没有它 ⇒ START 根本没进芯片，
不必再查窗口时长、复位时机、容量校验。

反向佐证：`ESP32_READY_CMD_WAIT` / `NEED_BURN` / `FLASH_SIZE` 连刷 9 轮。
固件窗口 5000ms、每 500ms 喊一次（[bsp_flash.c:282-290](../../../../main/bsp/bsp_flash.c#L282-L290)），
9 轮 ≈ 4.5s ＝ 窗口从头到尾没收到任何命令，最后走
[bsp_flash.c:338](../../../../main/bsp/bsp_flash.c#L338) 的"挂载成功直接 return"。

## 三、根因

[3.py](../../../../3.py) 旧代码：`ser.dtr = False  # 防止重启`

ESP32-S3 用的是**内置 USB-Serial-JTAG**，标准 CDC-ACM 设备，DTR 语义是
「host 已打开此串口」。**DTR=False 时 host 写出的字节不会交付到设备的
USB-JTAG RX FIFO**，固件 `usb_serial_jtag_ll_read_rxfifo()` 恒读到 0。

⭐ **方向不对称**：设备→PC 的日志照收（所以看着一切正常），只有 PC→设备被堵死。
这就是"日志完美、命令石沉大海"的全部成因。

那句旧注释错在把 USB-JTAG 当成了 CH340/CP210x：外置 UART 芯片配自动下载电路时
DTR/RTS 接 GPIO0/EN，置位才复位；**S3 内置 USJ 的 DTR 纯是流控信号，置 True 不复位**。
⚠️ 但 `hard_reset_board()` 里的 DTR=False 是对的别动——那里刻意用 RTS 拉 EN 复位，
且要避免掉进 ROM 下载模式，与数据通道是两码事。

**为什么以前能烧、现在才炸**：隐患一直在，只是被容错掩盖。以前外挂 flash 是空的
→ 挂载失败 → 走 [bsp_flash.c:360](../../../../main/bsp/bsp_flash.c#L360) 的**无限**监听循环，
设备一直等、脚本反复重试总能撞上；现在板子烧成功过 → 挂载成功 → 只剩 5 秒窗口，
容错没了，隐患立刻暴露。

## 四、修改点（全在 3.py，固件一行未动，**未做语法自检**）

| 位置 | 改动 |
|---|---|
| `ser.dtr = True`（open 前） | 核心修复；RTS 保持 False 免得拉 EN 复位 |
| open() 之后再置一次 DTR/RTS | 部分驱动 open 时按默认值重新驱动控制线，会覆盖 open 前的设置 |
| `global DEVICE_FLASH_SIZE` | 函数内有赋值 → Python 整个当局部变量，模块级全局量形同虚设；旧版靠每轮先赋 None 才没抛 UnboundLocalError，属侥幸 |
| 新增 `STARTING_ERASE` 确认循环 | 见下 |
| `ser.write()` 后 `flush()`、不吞异常 | 用户自己加的，方向对：pyserial write 带缓冲，不 flush 可能还躺在 OS 队列 |

**确认循环（比修 DTR 本身更值钱）**：发完 START 不再盲目宣布"已送达"，
改为等 `STARTING_ERASE` 最多 6s，其间每见一次 `ESP32_READY_CMD_WAIT` 就补发一次
START（榨干剩余窗口），超时则明确报错 continue 重试。
旧版没这步，命令没送进去时照样打印"已送达"，然后**卡死在等 `READY_FOR_DATA` 的
`while True` 死循环**——排查者看到"卡住"，真相是"命令从没到过"。

## 五、第二个阻断点：固件 `fgetc(stdin)` 绑的是没接线的 UART0 ⭐

DTR 修好后仍烧不进，说明**同时存在第二处单向阻断**，两者叠加、缺一不可。

**根因**：本项目 sdkconfig 的 console 配置——
```
CONFIG_ESP_CONSOLE_UART_DEFAULT=y              ← 主 console = UART0
CONFIG_ESP_CONSOLE_SECONDARY_USB_SERIAL_JTAG=y ← USB-JTAG 仅"次要"
```
**secondary console 是单向的：只镜像输出、不接管输入。**
`printf` 会镜像到 USB-JTAG（PC 看得到日志），但 `stdin` 只绑 UART0，
而板子是 USB 线连电脑、UART0 物理上没接线 ⇒ `fgetc(stdin)` 永远读不到 PC 命令。

⭐ 症状与 DTR 坑**完全一致**（日志正常刷、命令石沉大海、窗口喊满转正常挂载），
判定指纹同样是"没有 STARTING_ERASE"，所以排查时必须**两个都查**。

**修复**（bsp_flash.c，两处监听循环）：改直读 USB-JTAG 硬件 FIFO 绕开 stdin
```c
#include "hal/usb_serial_jtag_ll.h"   // 新增
uint8_t rxbuf[64];
int n = usb_serial_jtag_ll_read_rxfifo(rxbuf, sizeof(rxbuf));
```
位置：强制烧录窗口段、挂载失败后的持续监听循环。
⚠️ 不能改用 `usb_serial_jtag_read_bytes()`——那要先 install 驱动，
而驱动必须留到真进产线后再装（装早了 ISR 干扰 I2C 时序，见 BUG-015）。

**顺带修**：命令缓冲区原每轮 `memset` 清空，USB 分片到达时
（`START\n` 拆成 `ST` + `ART\n`）会丢掉半个命令。已改跨轮询累积、仅将满时清空。

## 六、16MB/32MB 自动适配（同日落地）

各板外挂 flash 容量不统一（板A=32MB / 板B=16MB），现已全自动、无需人工判断：

**固件侧**（bsp_flash.c）
- 新增 `s_real_flash_size`，`esp_flash_get_size()` 后赋值；擦除/烧录/提取三处
  循环边界全改用它，**不再用写死的 `TOTAL_FLASH_SIZE` 宏**（旧宏固定 32MB，
  在 16MB 板上会越界擦写）。
- 两处握手锚点后新增 `printf("FLASH_SIZE:%lu\n", flash_size)`。
  ⚠️ **这行以前根本不存在**——3.py 等它等不到，白等 8 次 readline（≈4s），
  反把固件那 1s 窗口熬没了，是排查途中的一条歧路。

**PC 侧**
- 2.py 支持 `python 2.py 16M` / `32M` / 纯字节数，不传参默认 32MB。
- 3.py `repack_storage_bin()`：容量不符时**自动调 `python 2.py <真实字节数>`
  重打包并重试**，不用人工敲命令。
  ⚠️ `subprocess.run` 必须带 `encoding='utf-8', errors='replace'`，
  否则 Windows 默认 GBK 解不了 2.py 的中文/emoji，抛 `UnicodeDecodeError`。

**遗留取舍**：为抢固件窗口，START 在容量校验**之前**发。真遇容量不符时设备已进
擦除态，自动重打包后需断电重插才能重试。规避：烧录前先打成正确容量，让自动重打包只作兜底。

## 七、教训

1. **发命令后必须等设备的肯定回执，不能拿"write 没报错"当成功。**
   write 成功只证明字节进了 OS 缓冲，不证明设备收到、更不证明执行了。
2. 每个关键动作都要有**设备侧锚点**（这里是 STARTING_ERASE）；诊断先问
   "哪条本该出现的日志没出现"——同 BUG-031 马达短路那次的夹逼法。
3. **靠"多试几次总能成"活着的链路等于没修**，换个场景必复发（本例正是如此）。
4. 串口握手三大自废姿势合集：**按行数计循环**（BUG-024 续集一）、
   **不置 DTR**、**不等回执**（本次两条）。
5. **同症状可能有多个独立根因叠加**：DTR 与 stdin/UART0 两处都造成"PC→设备
   单向堵死"，只修一个照样不通。修完一处没好转，别急着推翻结论，先想有没有第二处。
6. ESP-IDF 的 primary/secondary console **不对称**：secondary 只镜像输出，
   输入永远走 primary。设备要读 PC 命令时不能想当然用 stdin。

详见系统记忆 BUG-024 续集二、续集三。
