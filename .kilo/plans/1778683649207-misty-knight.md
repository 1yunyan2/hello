## 二、PSRAM 泄漏分析（~296 KB / 次）

### 2.1 各组件 PSRAM 占用量

| 组件 | 分配方式 | 大小 (B) |
|------|---------|---------|
| enc_input ringbuf | xRingbufferCreateWithCaps(SPIRAM) | 131,072 |
| enc_output ringbuf | xRingbufferCreateWithCaps(SPIRAM) | 32,768 |
| dec_input ringbuf | xRingbufferCreateWithCaps(SPIRAM) | 16,384 |
| dec_output ringbuf | xRingbufferCreateWithCaps(SPIRAM) | 40,960 |
| aec_ref_buf ringbuf | xRingbufferCreateWithCaps(SPIRAM) | 8,192 |
| **Ring buffer 小计** | | **229,376** |
| encoder_task 栈 | xTaskCreatePinnedToCoreWithCaps(SPIRAM) | 32,768 |
| decoder_task 栈 | xTaskCreatePinnedToCoreWithCaps(SPIRAM) | 32,768 |
| play_task 栈 | xTaskCreatePinnedToCoreWithCaps(SPIRAM) | 4,096 |
| ws_sender_task 栈 | xTaskCreatePinnedToCoreWithCaps(SPIRAM) | 4,096 |
| **任务栈小计** | | **73,728** |
| encoder/decoder 结构体 + OPUS 内部状态 | malloc_zeroed + esp_audio_enc/dec_open | ~数 KB |
| **总计** | | **~303 KB** |

### 2.2 根因：任务栈延迟释放

**验证过程：**

```
Ring buffer 后 PSRAM: 3,178,352 (分配 272,164 B ≈ 266 KB, 含 ringbuf 元数据)
任务启动后 PSRAM:    3,099,700 (再分配 78,652 B ≈ 77 KB)
销毁后 PSRAM:        3,147,180 (释放 47,480 B ≈ 46 KB)
```

- `vRingbufferDelete()` 是**同步操作**，调用后立即释放内存 → Ring buffer (229 KB) **已释放** ✓
- `vTaskDelete()` 只标记任务为"待清理"，**实际的栈+TCB 释放由 IDLE 任务执行** → 任务栈 (72 KB) **尚未释放** ✗
- `audio_processor_destroy()` 中的 `vTaskDelay(100ms)` **不足以让 IDLE 任务清理完 4 个被删除任务的栈**

**数学验证：**

```
净损失 303,508 B
- Ring buffer 释放 229,376 B（同步，已释放）
= 剩余 74,132 B

任务栈理论值: 73,728 B
差值: 74,132 - 73,728 = 404 B（≈ FreeRTOS TCB 结构体开销）
```

**结论：PSRAM "泄漏" 是任务栈延迟释放，非真正泄漏。** IDLE 任务运行后会自动回收。但 100ms 快照时间点无法反映真实释放量。

### 2.3 验证方法

在 `audio_processor_destroy()` 的 `vTaskDelay(100)` 后再追加一次 `vTaskDelay(2000)` (2 秒)，然后重新打印内存快照。如果 PSRAM 恢复到接近会话前水平，则确认为延迟释放。

## 三、内部 SRAM 泄漏分析（~2.7 KB / 次）

### 3.1 可能来源

| 来源 | 估计大小 | 是否在 100ms 内释放 |
|------|---------|-------------------|
| FreeRTOS TCB（4 个任务 × ~300 B） | ~1,200 B | 否（IDLE 任务释放） |
| mbedTLS session ticket 缓存 | ~200-500 B | 不确定 |
| WebSocket 接收帧临时缓冲 | ~200-500 B | 通常释放 |
| heap 碎片化（不可回收的空洞） | ~500-1,000 B | 不可回收 |

### 3.2 结论

~2.7 KB 的内部 SRAM 损失主要来自：
1. **TCB 未释放** (~1.2 KB)：与 PSRAM 任务栈同理，IDLE 任务尚未清理
2. **Heap 碎片化** (~1.5 KB)：频繁 alloc/free 大小不同的块导致碎片

少量累积不会引发 OOM（当前空闲 59 KB），但长期运行（数百次会话后）可能使最大连续块缩小。

## 四、Sender Task 退出竞态问题

### 4.1 问题描述

日志证据：
```
W (106683) Session: sender 任务未能在超时内退出
I (106803) Session: 发送任务结束，共发送 190 帧 OPUS
```

`session_close()` 等待 `ws_sender_task` 退出 1 秒超时后，直接调用 `audio_processor_destroy()`，此时 sender 任务仍在运行。~120ms 后 sender 才自行退出。

### 4.2 风险

- `audio_processor_destroy()` 调用 `vRingbufferDelete(enc_output)` 时，sender 可能正在 `audio_processor_read_timeout()` 中读取 `enc_output`
- 虽然当前未崩溃（sender 大概率在 vTaskDelay 或 xEventGroupGetBits 中），但存在 **use-after-free 竞态风险**

### 4.3 Sender 退出慢的原因

sender 任务的退出路径：
```c
while (s_state == SESSION_LISTENING || s_state == SESSION_PLAYING)
{
    // ...
    size_t len = audio_processor_read_timeout(s_processor, buf, sizeof(buf), 100);
    // protocol_send_audio_data() — 网络发送，耗时不定
}
```

当 `s_state` 被设为 `SESSION_IDLE` 后，sender 需等待：
1. 当前 `audio_processor_read_timeout` 最多 100ms 超时返回
2. 如果正在 `protocol_send_audio_data()`，网络阻塞可能数百毫秒

总延迟可能 > 1 秒。

## 五、dec_output 持续欠载问题（非泄漏，附带分析）

日志中大量出现：
```
W (282293) Audio Processor: dec_output 持续欠载 60 ms，重新进入预缓冲
```

**原因：** TTS 数据通过 WebSocket 下发后，解码器输出到 `dec_output` 的速率与 `play_task` 消费速率不匹配。在 TTS 预缓冲阶段（600ms），解码器尚未积累足够数据，play_task 反复读空 → 触发 underrun → 重置预缓冲。

**影响：** 不是内存问题，但造成：
- CPU0 额外开销（频繁状态切换）
- 可能的音频卡顿

## 七、结论与建议

### 真正的泄漏 vs 延迟释放

| 类别 | 大小 | 性质 | 是否真正泄漏 |
|------|------|------|-------------|
| PSRAM 任务栈 | ~72 KB | IDLE 任务延迟释放 | ❌ 延迟释放 |
| PSRAM Ring Buffer | ~229 KB | vRingbufferDelete 同步释放 | ❌ 已释放 |
| PSRAM OPUS 状态 | ~数 KB | esp_audio_enc/dec_close 释放 | ❌ 已释放 |
| Internal TCB | ~1.2 KB | IDLE 任务延迟释放 | ❌ 延迟释放 |
| Internal 碎片 | ~1.5 KB | heap 碎片化 | ⚠️ 累积性 |

### 需要修复的问题

1. **audio_processor_destroy 的 100ms 等待不足**：改为等待 200-500ms，或主动查询任务句柄确认已为 NULL
2. **sender task 退出竞态**：`session_close` 应确保 sender 已退出后再调用 destroy，超时后应 `vTaskDelete` 强制终止 sender
3. **Internal SRAM 碎片**：长期运行需监控 `heap_caps_get_largest_free_block(MALLOC_CAP_INTERNAL)` 是否持续下降
