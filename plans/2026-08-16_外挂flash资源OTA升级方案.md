# 外挂 flash 资源 OTA 升级方案

日期：2026-08-16
状态：待编码（方案已定：MQTT 触发 + NVS 独立资源版本号 + 按文件增量下载）

## 一、背景与目标

外挂 flash（SPI3，FAT 文件系统挂载 /S）当前只能靠产线 USB 整盘烧录更新，
无法远程迭代。目标是让后端能通过 MQTT 指令远程增量更新 /S 下的资源文件
（GIF / 图片 / 字体 / 离线音频）。

现有两套更新通道（均不覆盖外挂 flash 资源）：
- 固件 OTA：bsp_ota.c 走 esp_https_ota 只写内置 flash ota 分区
- 产线烧录：bsp_flash.c start_production_burning 走 USB 整盘擦写

## 二、方案定稿

按文件清单增量下载：后端下发 manifest（文件清单），设备逐个文件
HTTP 下载 → 临时文件 → SHA256 校验 → rename 原子覆盖 → 全部完成后重启。

### 协议（MQTT command 主题，新增 ota_resource 分支）

```json
{
  "type": "ota_resource",
  "version": "1.2.0",
  "files": [
    {
      "path": "/S/gif/new.gif",
      "url": "https://cdn.example.com/gif/new.gif",
      "sha256": "ab12cd34...",
      "size": 12345
    }
  ]
}
```

- version：资源版本号（语义化，独立于固件版本）
- files：本次要更新的文件清单；path 是目标绝对路径（以 /S 开头）

### 上报（resource-status 主题，对齐 ota-status 口径）

`echopal/device/{id}/resource-status`
```json
{"status":"upgrading|success|failed","progress":0~100,"version":"1.2.0","errorMsg":"","timestamp":...}
```

### 设备侧流程

1. MQTT 收到 ota_resource → 版本比较（NVS res_ver），<= 则跳过
2. 创建下载任务（INTERNAL 栈，见下）
3. 逐个文件：HTTP GET 流式下载 → 写 /S/xxx.tmp → SHA256 → rename 覆盖
4. 全部完成 → 写 NVS res_ver = version → 上报 success → esp_restart()
5. 任一失败 → 上报 failed（带中文原因），不重启（旧资源因原子 rename 不受损）

## 四、关键技术处理点

1. **下载任务栈必须 INTERNAL**（BUG-039 铁律）：fwrite 到 FAT → wl 层写 flash
   → 禁用 Cache，SPIRAM 栈此时不可访问必 panic。对齐 bsp_ota.c:510 写法：
   `xTaskCreatePinnedToCoreWithCaps(..., 8192, MALLOC_CAP_INTERNAL|MALLOC_CAP_8BIT)`
2. **下载缓冲用 SPIRAM**：128KB 分块（对齐 BURNER_CHUNK），避免吃内部 SRAM。
   注意：缓冲是数据不是栈，放 SPIRAM 安全；栈才是 INTERNAL。
3. **升级前停用外挂 flash 的任务**：ui_pause_main_gif() + interaction_stop_for_ota()
   + offline_audio_stop()，避免读到写一半的文件。字体懒加载后已进内存不受影响。
4. **掉电保护**：临时文件 + rename 原子替换；残留 .tmp 开机清理。
5. **重启语义**：字体/图片开机加载进内存，升级后必须 esp_restart() 重新加载，
   否则改了字体不生效。固件 OTA 失败也是重启回退，资源 OTA 失败不重启（无副作用）。
